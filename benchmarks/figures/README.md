## 1. Overview and Design Standards

This directory contains the authoritative academic figures illustrating the systems performance investigations of KernelTick. All figures are generated directly from the empirical datasets in [`benchmark_results/`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results) using reproducible Python and Matplotlib scripts.

### 1.1 Academic Publication Standards
- **Monochrome / Grayscale Presentation:** Designed for black-and-white publication. Distinctions between configurations are achieved through grayscale shading, high-contrast borders, standard geometric markers (`o`, `^`), and distinct hatching patterns (`///`, `xxx`).
- **Data Integrity & Non-Truncated Axes:** Bar chart axes start at zero to avoid misleading scaling. Logarithmic axes ($\log_{10}$) are utilized specifically when displaying wide-dynamic-range metrics (such as latency tails or contention retries spanning orders of magnitude).
- **Separation of Metrics:** Operation latency (CPU execution time of a single method in nanoseconds) is strictly separated from End-to-End message dwell latency (in-queue residency time in microseconds).
- **Explicit Error Bars & Outlier Preservation:** Error bars explicitly denote either $\pm 1$ standard deviation ($\sigma$) or exact Min–Max ranges across independent repetitions. Individual run points are overlaid as scatter markers to preserve raw run distribution and make anomalies visible.

## 3. Detailed Figure Descriptions and Interpretations

### Figure 1: Limit Order Book Baseline Performance (Phase 2)
- **Filenames:** `figure1_order_book_baseline.png` / `figure1_order_book_baseline.svg`
- **Data Source:** [`benchmark_results/order_book_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/order_book_benchmark.csv) (10,000 operations per workload $\times$ 3 runs; 12 RUN records, 4 AGGREGATE records)
- **Subplots:**
  - **(A) Throughput across Workloads:** Bar chart showing Mean throughput in Million ops/sec. Error bars indicate Min–Max range across 3 repetitions. Individual runs are plotted as overlaid points.
  - **(B) Operation Latency Distribution (Log Scale):** Grouped bar chart comparing $P_{50}$ median latency and $P_{99}$ tail latency on a $\log_{10}$ nanosecond scale.
- **Key Empirical Interpretations:**
  - Pure order insertion and cancellation demonstrate high performance exceeding **11.5M to 12.5M ops/s**, with median operation latencies of **47.3 ns** (insertion) and **62.0 ns** (cancellation).
  - Mixed trading flow (40% Bids, 40% Asks, 10% Cancels, 10% Crosses) sustains **11.16M ops/s** with a $P_{50}$ of **43.3 ns**.
  - Continuous trade matching with partial fills drops to **546K ops/s** ($P_{50} = 1,313\ \text{ns}$, $P_{99} = 3,585\ \text{ns}$). This difference reflects the computational cost of continuous double-auction processing: validating order IDs, performing multi-level price ladder traversals, adjusting two-sided quantities, and allocating execution records.

### Figure 2: Memory Allocation Optimization (Phase 3)
- **Filenames:** `figure2_memory_pool_optimization.png` / `figure2_memory_pool_optimization.svg`
- **Data Source:** [`benchmark_results/memory_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/memory_benchmark.csv) (100,000 operations per experiment $\times$ 5 runs; 50 RUN records, 10 AGGREGATE records)
- **Subplots:**
  - **(A) Throughput Comparison across Allocation Patterns:** Grouped bars comparing Dynamic Heap (`new`/`delete` via glibc ptmalloc) against `OrderMemoryPool` across 5 allocation patterns. Error bars indicate $\pm 1$ standard deviation ($\sigma$). Individual runs are overlaid.
  - **(B) P99 Tail Latency Comparison (Log Scale):** Grouped bars comparing 99th percentile operation latency in nanoseconds.
- **Key Empirical Interpretations:**
  - **Tail Latency Compression:** In allocation-heavy patterns (Exp 1 and Exp 2A), the preallocated memory pool delivers a **42x reduction in $P_{99}$ tail latency** (falling from 3,944 ns down to 93 ns in Exp 1, and 4,197 ns down to 100 ns in Exp 2A). Throughput increases by **+77%** (Exp 1) and **+101%** (Exp 2A).
  - **Repeated Reuse (Exp 3):** Under 10 repeated allocate-free cycles, the pool achieves **+53% higher throughput** and slashes extreme $P_{99.9}$ tail latency by **27x** (3,694 ns down to 136 ns).
  - **Workload Where Dynamic Allocation Performed Better (Exp 4 — Window Churn):** In a sustained 1,000-order sliding window churn workload, **dynamic heap allocation achieved +11% higher throughput** (7.65M ops/s vs. 6.88M ops/s). A plausible interpretation is that glibc's per-thread cache (`tcache`) serviced allocations out of hot L1 cache without arena locks for this small 1,000-order working set, whereas `OrderMemoryPool` executed atomic 64-bit CAS loops on its Treiber stack. However, L1 cache residency and `tcache` hit rates were not directly measured with hardware performance counters. Importantly, `OrderMemoryPool` still preserved tighter tail bounds ($P_{99.9}$ of 132 ns for pool vs. 196 ns for dynamic).

### Figure 3: Queue Concurrency Synchronization (Phase 4)
- **Filenames:** `figure3_queue_concurrency.png` / `figure3_queue_concurrency.svg`
- **Data Source:** [`benchmark_results/concurrency_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/concurrency_benchmark.csv) (1,000,000 messages per run $\times$ 5 runs across 1K and 64K capacities; 20 RUN records, 4 AGGREGATE records)
- **Subplots:**
  - **(A) Queue Throughput Comparison:** MutexQueue vs. SPSCQueue throughput in Million ops/sec. Error bars indicate Min–Max range across 5 repetitions.
  - **(B) Operation Latency (ns, Log Scale):** Comparison of $P_{50}$ median and $P_{99}$ tail operation execution times.
  - **(C) End-to-End Dwell Latency (µs, Log Scale):** In-queue transit delay from producer enqueue to consumer dequeue.
- **Key Empirical Interpretations:**
  - **Throughput Advantage:** The lock-free Dmitry Vyukov ring buffer (`SPSCQueue`) achieves a **3.46x throughput advantage on 1K queues** (7.30M vs. 2.11M ops/s, +246.4%) and a **2.74x throughput advantage on 64K queues** (10.14M vs. 3.71M ops/s, +173.8%).
  - **Lock Contention Tail Penalties:** In `MutexQueue`, shared mutex acquisition causes severe cache-line serialization, driving $P_{99}$ operation latency to **1,046 ns (1K)** and **833 ns (64K)**, compared to **162 ns** and **149 ns** for `SPSCQueue`.
  - **Dwell Latency Collapse:** Eliminating lock serialization reduces 99th percentile queue dwelling time by **over 90%** (collapsing from 3.67 ms to 344 µs on 1K, and from 90.2 ms to 8.3 ms on 64K).

### Figure 4: Linux CPU Core Affinity (Phase 5.1)
- **Filenames:** `figure4_cpu_affinity.png` / `figure4_cpu_affinity.svg`
- **Data Source:** [`benchmark_results/cpu_affinity_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/cpu_affinity_benchmark.csv) (1,000,000 messages per run $\times$ 5 runs across 1K and 64K capacities; 20 RUN records, 4 AGGREGATE records)
- **Subplots:**
  - **(A) Throughput: Divergent Impact of Thread Pinning:** Mean throughput bars with $\pm 1\sigma$ error bars and overlaid individual run measurements.
  - **(B) Total Push Retries (Log Scale):** Total contention full-buffer push retries across the 5 independent runs.
- **Key Empirical Interpretations:**
  - **1K Capacity (Decisive Benefit):** In tight backpressure-sensitive queues, CPU affinity **improved mean throughput by +46.0%** (3.66M to 5.35M ops/s) and **median throughput by +68.0%** (3.16M to 5.31M ops/s). Under default CFS scheduling, Run #1 suffered a severe **193.56-second stall** (5,166 ops/s) with **848.5 million push retries**, consistent with co-scheduling stalls when spinning threads share a CPU core. Explicit pinning cut total push retries by **99.6%** (from 859.6M down to 3.1M).
  - **64K Capacity (Performance Penalty):** In large burst-absorbing queues, CPU affinity **reduced throughput by -47.8%** (10.77M down to 5.62M ops/s). One hypothesis is that rigid pinning restricted guest thread migration across virtual execution units, whereas unpinned CFS threads could float across available vCPUs. However, host-level scheduling, hypervisor thread multiplexing, and vCPU descheduling by the host operating system were not directly measured from within the guest.
  - **Architectural Takeaway:** CPU affinity is not universally beneficial; its effectiveness depends on buffer capacity, backpressure sensitivity, and execution environment characteristics (such as bare-metal dedicated cores versus virtualized vCPUs).

### Figure 5: Linux Thread Scheduling Policies (Phase 5.2)
- **Filenames:** `figure5_scheduling_policies.png` / `figure5_scheduling_policies.svg`
- **Data Source:** [`benchmark_results/scheduling_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/scheduling_benchmark.csv) (1,000,000 messages per run $\times$ 5 runs across 1K and 64K capacities, pinned cores 0 and 1; 20 RUN records, 4 AGGREGATE records)
- **Subplots:**
  - **(A) Throughput and Variance Comparison:** Mean throughput bars with $\pm 1\sigma$ error bars and overlaid individual runs.
  - **(B) Operation Latency (ns):** Comparison of $P_{50}$ median and $P_{99}$ tail latencies.
  - **(C) Consumer Empty-Pop Starvation Retries (Log Scale):** Total empty-pop retry loops across 5 runs.
- **Key Empirical Interpretations:**
  - **Consistent Throughput Improvements:** Real-time priority (`SCHED_FIFO`, priority 10) increased mean throughput by **+53.8% on 64K queues** (7.14M to 10.98M ops/s) and **+48.9% on 1K queues** (7.53M to 11.21M ops/s).
  - **Variance Suppression:** Throughput standard deviation on 64K buffers dropped by **52.5%** (from 1.67M to 793K ops/s). Every individual `SCHED_FIFO` run exceeded 9.70M ops/s.
  - **Fewer Starvation Retries:** Empty-pop consumer starvation retries collapsed by **-95.5% on 64K queues** (from 161.6K down to 7.3K) and by **-80.2% on 1K queues** (from 365.8K down to 72.5K). This demonstrates that real-time priority substantially reduced consumer polling retries, without proving the precise scheduling cause (as guest scheduler preemption cannot be conclusively isolated from host-level hypervisor scheduling dynamics).

### Figure 6: Virtual Memory Locking & Page Fault Analysis (Phase 5.3)
- **Filenames:** `figure6_memory_locking.png` / `figure6_memory_locking.svg`
- **Data Source:** [`benchmark_results/memory_locking_benchmark.csv`](file:///home/kali/Real-Time-Market-Data-Feed-Handler-and-Order-Matching-Engine/benchmark_results/memory_locking_benchmark.csv) (1,000,000 messages per run $\times$ 5 runs across 1K and 64K capacities; 20 RUN records, 4 AGGREGATE records)
- **Subplots:**
  - **(A) Throughput: Workload-Dependent Impact:** Normal demand paging vs. `mlockall(MCL_CURRENT | MCL_FUTURE)`.
  - **(B) Operation Latency (P50 & P99 in ns):** Comparison of median and tail execution latencies.
  - **(C) Page Faults (Delta from getrusage):** Cumulative minor page faults ($\Delta \text{MinFlt}$) and major page faults ($\Delta \text{MajFlt}$) across 5 runs.
- **Key Empirical Interpretations:**
  - **Workload-Dependent Throughput:** On 64K queues, memory locking provided a modest throughput gain of **+7.2%** (7.30M to 7.83M ops/s). On 1K queues, memory locking caused a slight throughput degradation of **-3.3%** (8.72M to 8.43M ops/s).
  - **Latency Trade-Offs:** On 64K queues, $P_{99}$ tail latency improved by **-12.9%** (155 ns down to 135 ns), but $P_{50}$ median latency increased by **+26.9%** (60.2 ns to 76.4 ns).
  - **Page Fault Dynamics:**
    - Major page faults ($\Delta \text{MajFlt}$) were **identically 0** across all 20 benchmark runs because guest available RAM (~867 MB) comfortably exceeded the process working set (~20 MB), preventing disk swap activity.
    - Minor page faults ($\Delta \text{MinFlt}$) were observed only in Run #1 (216 in Normal mode vs. 185 in Locked mode) during initial dynamic linker relocations and heap arena initialization; in Runs #2 through #5, minor faults were exactly 0 due to buffer recycling.
  - **Methodological Distinction:** `mlockall` guarantees that eligible locked pages are not swapped to disk; it does not eliminate CPU TLB misses or hardware MMU page table walks.
